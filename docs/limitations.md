# Limitations and Scope

## 1. Synthetic Data Limitation

AegisRisk AI uses a research-calibrated behavioural simulation approach to generate synthetic transaction data.

The dataset is not derived from Razorpay production transactions and must not be interpreted as a representation of actual Razorpay customer, merchant, transaction, or fraud data.

All transaction identifiers, customer identifiers, merchant identifiers, behavioural patterns, and fraud labels are synthetic.

---

## 2. No Production Data Claims

This project does not claim access to:

- Razorpay production transactions
- Razorpay customer identities
- Razorpay merchant identities
- Razorpay internal fraud labels
- Razorpay proprietary risk signals
- Razorpay internal fraud detection rules
- Razorpay confidential operational data

Any reference to Razorpay in this project describes the intended payment-platform context and not access to proprietary production information.

---

## 3. Simulation Assumptions

The simulator uses three categories of parameters:

### Calibrated parameters

Parameters informed by publicly available research, industry reports, academic literature, or other defensible external evidence.

### Assumed parameters

Parameters introduced where sufficiently specific public evidence is unavailable.

These values are explicitly documented rather than presented as observed production behaviour.

### Derived parameters

Parameters calculated from other simulation parameters or generated behavioural relationships.

Each important parameter should include its source category and an explanation of how the evidence or assumption was translated into the simulation.

---

## 4. Behavioural Simulation Limitation

Synthetic behavioural patterns are designed to create realistic experimental conditions.

They do not establish that real payment-platform users, merchants, or fraudsters behave according to exactly the same distributions.

Therefore, model performance obtained on the synthetic dataset should be interpreted as prototype evaluation rather than evidence of production-level fraud detection performance.

---

## 5. Fraud Label Limitation

Fraud labels are generated by the simulation process.

They are not verified real-world fraud outcomes.

Consequently:

- Precision does not represent production precision.
- Recall does not represent production recall.
- F1 score does not represent production F1.
- PR-AUC does not represent production PR-AUC.
- Cost estimates do not represent actual Razorpay financial losses.

These metrics are used to compare approaches consistently within the simulated environment.

---

## 6. Temporal Evaluation Limitation

The project uses chronological train, validation, and test splits to reduce unrealistic information leakage and better approximate deployment conditions.

However, chronological simulation does not guarantee that all real-world temporal effects are reproduced.

Real payment systems may experience:

- New fraud strategies
- Seasonal behaviour
- Changing merchant behaviour
- Changes in payment methods
- Changes in customer behaviour
- Economic changes
- Policy or regulatory changes
- Adversarial adaptation

These effects require real-world monitoring and future validation.

---

## 7. Feature Availability Constraint

The modelling pipeline is designed to use only information available at the time a transaction decision is made.

The system must not use:

- Future transactions
- Future fraud labels
- Post-transaction outcomes
- Future aggregates
- Information created after the decision timestamp

This constraint is essential for preventing temporal leakage.

---

## 8. Model Generalisation

A model that performs well on this synthetic dataset may not generalise to a real payment environment.

Production deployment would require validation using appropriately governed real-world data, monitoring, calibration, drift detection, human review procedures, and controlled experimentation.

---

## 9. Cost Model Limitation

The project uses simulated or assumed economic costs to demonstrate cost-aware decision making.

These costs are not claims about actual Razorpay losses, chargeback costs, operational costs, or customer-impact costs.

The cost model should therefore be treated as an experimental decision framework.

---

## 10. Scope Limitation

The Day 1 foundation focuses on a unified transaction fraud-risk management prototype.

Return fraud, chargeback fraud, and account takeover are not implemented as separate full models during the foundation phase.

They may be considered as future extensions after the core transaction-risk pipeline has been validated.

---

## 11. Reproducibility

The simulation is designed to support reproducibility through:

- A fixed configurable random seed
- Configuration stored separately from implementation code
- Version-controlled source code
- Explicit parameter categories
- Documented assumptions
- Validation of configuration values

Changing the seed or simulation parameters may produce different synthetic datasets and therefore different model results.

---

## 12. Intended Use

AegisRisk AI is intended for:

- Prototype development
- Research experimentation
- Model comparison
- Fraud-risk workflow demonstration
- Evaluation of temporal modelling approaches
- Evaluation of cost-aware decision strategies
- Explainability experiments

It is not intended to make claims about actual Razorpay production fraud rates, customer behaviour, merchant behaviour, or production model performance.
